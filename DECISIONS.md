# Ledger architectural decisions

Historical Checkpoint 1 decisions · 2026-10-19 UTC (2026-10-18 in Mexico City at request).

1. **Checkpoint boundary.** Implement only the transaction foundation. Home has elementary month totals/category totals, not analytical modes, budgets, or recurring schedules. No import/export/backup handlers or placeholder simulated finance data.
2. **Static React/TypeScript/Vite PWA.** Static HTTPS deployment needs no backend or paid runtime. All dependencies/assets are bundled. Relative URLs support GitHub Pages subfolders. User performs final hosting/account steps; no deployment was done.
3. **IndexedDB through idb.** Database `ledger`, schema v1, stable UUID relationships, indexed local date/category/merchant, unique normalized merchant names, atomic seeding and commits. Preferences stay in IndexedDB too. Schema upgrade code is centralized. Future versions must upgrade v1 rather than replace it.
4. **Integer centavos and positive amounts.** Type determines sign. Refunds are separate from income: gross = expenses; net spending = expenses − refunds; cash flow = income + refunds − expenses. Negative net spending is valid. Parse decimal strings; reject precision beyond cents, zero/negative entries, scientific notation, and amounts over 999,999,999.99 MXN. Filter boundaries may be zero. Guard unsafe sums.
5. **Recorded local calendar fields.** Store instant plus local day/time. Reports group the entry's recorded local day, avoiding UTC month-boundary errors or travel regrouping. Overrides use current device timezone; nonexistent times are rejected, ambiguous DST times use the earlier JavaScript occurrence. Future schedules must use local-calendar arithmetic and explicitly define month-end clamping; recurrence is not implemented yet.
6. **Archive, never delete category/merchant records.** Renaming resolves through stable IDs, so history displays the current name. Archival hides new-entry choices while allowing existing entries to retain them during edits. Other/Other Income cannot be archived or renamed. Merchant uniqueness includes archived merchants; unarchive to reuse. Category type cannot change.
7. **Optional merchant and independent description.** Shared merchant pool for all types. Default category is an explicit suggestion button, valid only for the current type. Each fresh entry starts with no merchant; no prior amount/description is reused.
8. **Duplicate prevention.** A synchronous form lock plus disabled button handles rapid taps; one UUID per unsaved entry plus IndexedDB `add` handles repeated writes. Identical intentional purchases remain allowed. Failed writes retain input. A sparse unique `occurrenceKey` index is ready for Checkpoint 2's exactly-once recurrence; no schedules are processed here.
9. **Native modal dialogs.** Browser-managed focus trapping and Escape behavior, labeled controls, visible focus, generous touch targets. Notices repeat inside dialogs because their native top layer would obscure an external toast. Browser rendering/focus behavior remains subject to manual QA.
10. **Prompted worker updates.** Workbox precaches the full static application. Updating does not reload an unfinished form silently. No financial records are cached as HTTP responses; they live in IndexedDB. No background execution or push dependency.
11. **Minimal themes and one-hand entry.** System appearance default; preference persisted. Local system fonts, neutral surfaces, restrained positive/error colors, Lucide icons. Four tabs with Add as fresh-start destination. Resume keeps current work, not forced navigation.
12. **Simple personal-data scale.** Atomic snapshots in memory plus 60-row incremental history rendering. Existing indexes allow future query pagination without data changes. No unmeasured large-dataset performance claims. Multiwindow refresh via BroadcastChannel/focus; concurrent edits are last-write-wins.
13. **Forward compatibility.** Optional transaction fields `automatic`, `recurringScheduleId`, `occurrenceKey`, and `originalExpenseId` support later features. Budgets/schedules will receive their own stores via a v2 upgrade. Backup format/version validation and merge/replace semantics are deferred to Checkpoint 3.
14. **Honest verification.** Vitest/jsdom/fake-indexeddb test logic and interactions; they do not replace a real browser. Production manifest/precache checks are static checks. No supported browser automation surface was available, so no preview server, screenshots, Safari claims, or deployment claims were made.


## Historical Checkpoint 2 decisions — 2026-10-19

These extend/supersede the historical checkpoint boundaries and schema notes above. At that checkpoint, only Checkpoint 2 was approved; the current Checkpoint 3 decisions below supersede that boundary.

15. **Exact continuation.** Original source/package/tracking files were compared with the delivered Checkpoint 1 archive before editing. Baseline tests/build were green. No recreation, dependency upgrade, new backend, or chart dependency.
16. **Additive schema 2.** Preserve every v1 store and index. Create `schedules`, `occurrences` (indexed by schedule), and `budgets`; merge only the new Basic summary preference. Native IDB requests keep preference migration inside the atomic versionchange transaction. Observe completion rejection on aborts; never wipe/reseed an initialized database. Test v1 fixture preservation, reopen, aborted upgrade rollback, and old-client refusal.
17. **Occurrence ledger plus cursor.** A receipt keyed `scheduleId:scheduledDate` stores generated/deleted/skipped state and original transaction ID where applicable. It is separate from financial rows. Generated transactions, receipts, and processed-through date share one readwrite transaction over all affected stores. This serializes independent windows without advisory locks or localStorage. The pre-existing unique transaction occurrence index is a second invariant and can reconstruct a missing generated receipt.
18. **Deletion remains a deletion.** Deleting a generated row writes a durable tombstone in the same commit; editing keeps its original occurrence key even if date/type/amount changes. Schedule deletion keeps financial rows and all receipts. Receipt retention is intentional and future backup/restore must preserve it. No automatic pruning or cursor reset.
19. **Local Gregorian anchors.** Due enumeration uses date-only arithmetic. UTC is a calculator for Gregorian dates, not a source for local reporting days. Daily/weekly iteration advances civil dates; monthly/yearly dates clamp from the original anchor without drift. Gregorian century rules are tested. Due days post at local midnight; a midnight gap normalizes to the first represented time on that date. A completely skipped date gets a skipped receipt. Calendar inputs support 1000–9998.
20. **Prospective schedule edits.** Atomically settle old unprocessed dues through today using old terms, then save changes with the resulting cursor. New terms apply only after today; existing entries are untouched. Newly introduced historical dates are not backfilled by editing. A new schedule can intentionally backfill from its own start. This avoids retroactive frequency changes creating unexpected historical expenses.
21. **Pause policy.** Reconcile before pausing. While paused, due dates get skipped receipts and advance the cursor. Resume first reconciles through the current date while still paused; the resume day is skipped. The next eligible anchored date posts normally. This prevents an absence of app launches from turning paused periods into a backlog. Policy is stated beside the controls.
22. **Automatic lifecycle.** Launch plus focus/pageshow/visible-resume reconciles. Commit results populate a nonblocking in-app list. The list is session-local and shown by the window creating the entries; durable receipts provide integrity. No background execution, timer guarantee, push or remote clock. Failure rolls back the batch, shows an explicit error/retry, and leaves manual tracking available.
23. **Archive compatibility.** Existing schedules retain archived category/merchant references and continue to generate under them. New/changed selections require an active compatible entity. Archived entities are never hard-deleted, so existing scheduled relationships remain valid.
24. **Recurring positive monthly budgets.** One overall limit and optional category limits repeat until edited/removed. These are not historical allocation snapshots. Usage is expense minus refund received in the month; income is excluded and automatic rows are ordinary financial inputs. Excess refunds allow negative usage and availability above the limit; progress clamps to [0,1] and monetary overages remain explicit. Category limits are independent, not added to overall. Warnings at 80/100% never block writes.
25. **Summary semantics.** Persist the user mode. Ranges are inclusive recorded-local dates; presets include current periods, previous month, rolling 30 days, all, custom. Net daily average divides by calendar days including empty days and rounds half away from zero. Month deltas compare adjacent buckets inside the selected range; partial edge months are disclosed. Current-month budgets are separately labeled, independent of analytical dates. Merchants show gross expense/refund/net, not income disguised as spending.
26. **Local accessible charts.** Custom SVG lines, HTML series controls and period slider avoid another runtime dependency. Exact selected-period totals are text, not tooltip-only information. Category bars are tappable for details. Trend periods cap at 2,000; request a coarser interval instead of rendering an enormous chart. Real-device accessibility and layout acceptance still require manual QA.
27. **Verification boundary.** Full automated suite plus lint, explicit TypeScript, production and static-PWA checks pass. Additional Mexico City and New York DST tests are included. No supported real-browser capability was available, so no Safari/device/offline-runtime/deployment claim. Checkpoint 3 transfer/backup features were not implemented.

## Checkpoint 3 decisions — current, 2026-10-19

User explicitly approved this final checkpoint. These supersede earlier historical notes deferring transfers/backups. Version 1.0.0, schema 3; stop after delivery.

28. **Additive v3 migration.** Keep every v1/v2 store/index/record. Add `imports` with fingerprint/source indexes. Reminder preferences are optional, with absence meaning off. No reset/reseed. Migration fixtures include actual v2 schedules, tombstones and cursors; v1 compatibility remains tested.
29. **Complete consistent snapshots.** Capture all nine stores under one readonly transaction. JSON format `ledger-backup`, formatVersion 1, independent databaseVersion 3. Preserve relationships, recorded dates/instants, generated/deleted/skipped occurrence receipts, cursors, import provenance, preferences and metadata. Optional undefined properties serialize as absence, preserving application meaning.
30. **Strict whole-file validation.** Validate known format/store/record fields, duplicate keys/names, numbers, calendar strings, fallback categories, entity/refund links, preferences, budget relations, normalized merchant names, receipt/transaction agreement and cursor bounds. Deleted schedules/imported rows can legitimately leave provenance IDs; do not require those historical entities to be live. Backup wall-clock times are not reinterpreted in the destination timezone. Reject unknown future versions instead of silently discarding fields.
31. **Atomic restore and stale-preview guard.** Replace/merge are first planned and validated with a canonical baseline. Commit reacquires an all-store readwrite lock, compares the baseline and clears/repopulates inside that same transaction. Any failure aborts all writes, including clears. No file parsing, dynamic imports or non-IDB asynchronous work occurs while the write transaction is active.
32. **Deliberate restore modes.** Replace restores the complete point-in-time snapshot, explicitly undoing changes/deletions after it. Strict merge retains current preferences/metadata, unions identical/compatible records and rejects any differing same-ID record or normalized-entity conflict. Occurrence deletion/generated disagreements and schedule cursor differences are conflicts; do not guess winners or silently remap identities. User acknowledges a concrete preview before committing.
33. **Manual-only append imports.** Spreadsheet rows can create manual transactions and compatible entities, never schedules/occurrence identities/links. Known Ledger automatic markers and recurring identity columns are excluded even if the mapping omits Automatic. Preview shows exclusions. Exact recurrence state moves via JSON. Existing automatic IDs/content still participate in duplicate checking, including deleted occurrence transaction IDs.
34. **Durable import deduplication.** Track source/transaction IDs and normalized content fingerprints in a separate import receipt store, retained after deletion. Compare current records, prior import receipts, and within-file rows; recheck provenance inside the atomic commit. All invalid rows block the batch; duplicates/exclusions are skipped as previewed. Conservative duplicates can be entered manually when intentional. Never overwrite existing financial rows as an import side effect.
35. **Flat genuine spreadsheets.** Papa Parse handles CSV quoting and protected formula-like text; a version marker permits reversible escaping on Ledger exports. ExcelJS writes real numeric MXN cells and literal text with independent date/time columns, plus numeric Summary totals. No merged/day-group rows, formulas, external services or evaluation. Import rejects formula/hyperlink/rich-text cells instead of trusting cached values. ISO dates or real Excel date cells avoid ambiguous locale guessing.
36. **Offline lazy tooling.** Lazy-load DataTools and the ExcelJS browser bundle while Workbox precaches both. Normal entry remains a small separate UI bundle; transfer still works offline after full initial cache installation. The generic Excel chunk-size warning is expected and documented rather than hidden.
37. **Honest backup reminders/downloads.** Default off, local calendar-month reminder, persisted dismissal. Browser download initiation is not proof of file save; the user presses “I saved this backup” afterward to record a confirmed timestamp. No push, background task, cloud upload or external automation was added. Restoring older reminder preferences may make a reminder appear again, as expected.
38. **Bounds and memory.** Spreadsheet inputs: 10 MiB / 50,000 rows / 80 columns; JSON download/restore: 50 MiB / 1,000,000 records. Never emit a partial oversize backup. Snapshot/merge/validation stay in memory; no unmeasured maximum-size performance promise. XLSX uses Transactions if available, otherwise first worksheet, as disclosed in the UI.
39. **Accessibility refinements and verification.** Native dialogs gain explicit accessible names/focus return; add skip navigation, semantic/keyboard-accessible preview tables, responsive mappings and viewport keyboard spacing. Preserve reduced motion, touch targets, safe areas and local fonts. Only DOM behavior is verified here: no supported real-browser capability was present, so layout, Safari, downloads and runtime offline acceptance remain manual.
40. **Dependency-audit disclosure.** Production audit flags ExcelJS/uuid for GHSA-w5hq-g745-h8pq (one transitive advisory represented by two moderate package entries). Source inspection shows ExcelJS uses no-buffer uuid v4 calls, while the advisory affects v3/v5/v6 external output buffers. Ledger IDs use crypto.randomUUID. This is a documented applicability assessment, not removal of upstream bundled code or a clean-audit claim. No risky automatic dependency downgrade/override was applied merely to hide the report.
